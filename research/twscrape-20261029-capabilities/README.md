# twscrape 可引入能力评估

研究日期：2026-10-29。对象：Tweet-Watcher-v2 `0.1.0-beta.3`，源码 `b7bf16be35b5df8063ba1d5a1c8de62c148c21ee`。本文是候选功能评估，不代表已经实现、排期或完成真实采集验证。

## 结论与建议顺序

最值得引入的是 **X 会话健康与限流调度、引用上下文与媒体展示、帖子类型与关键词筛选**。随后根据需求增加明确包含回复的时间线、文章/对话补充，以及 List/关键词来源。账号池适合确有多个登录会话和容量需求时再做。

当前程序保留了采集完整性、持久队列和独立发送确认等重要约束。新增能力应继续通过现有受限桥接保存整页后自行校验；不能直接用上游高层迭代器替代完整性判断。

| 建议阶段 | 能力 | 用户收益 | 新增 X 请求 | 相对工作量 |
|---|---|---|---|---|
| 第一阶段 | 会话健康、共享限流冷却、有限重试 | 知道 Cookie 是否最近验证成功、为什么失败、何时重试 | 通常复用正常请求结果 | 中 |
| 第一阶段 | 引用作者/正文、图片/视频缩略图链接 | 阅读消息时看到原帖背景和媒体入口 | 已随当前页返回时不增加 | 中 |
| 第一阶段 | 原创/转推/回复/引用标识、未来新帖筛选 | 减少无关推送，保留关注的信息 | 本地过滤不增加 | 低至中 |
| 可靠性专项 | 采集与投递分开调度、持续追赶缺口 | 慢翻译不拖延其他目标，超预算缺口能继续补采 | 补采需要后续页 | 中至高；属于本程序设计 |
| 第二阶段 | “帖子与回复”监控 | 收到作者在回复里发布的信息 | 换用另一个时间线操作，可能更多分页 | 中 |
| 第二阶段 | 按需推文详情、对话背景、Article 摘要 | 连续讨论和长文章更易理解 | 通常需要额外详情查询 | 中至高 |
| 扩源阶段 | List 成员导入 / List 聚合 / Latest 关键词搜索 | 批量管理关注账号、发现主题信息 | 新来源及分页 | 成员导入中；聚合来源高 |
| 按容量决定 | 多登录会话池、受控代理 | 符合实际网络和可用性需求时使用 | 取决于策略 | 高 |

以上顺序是建议。自然新增推文的端到端生产验收、长期观察仍按[当前验证摘要](../../docs/VERIFICATION.md)执行，不因本次研究而标记完成。

## 一、会话健康与限流：最值得先做的稳定性功能

上游 [QueueClient](https://github.com/vladkens/twscrape/blob/63f61a518e576ea5c132f1156c03dda0520d76c1/twscrape/queue_client.py#L286) 使用 `x-rate-limit-remaining` 和 `x-rate-limit-reset`，账号池按登录身份与 GraphQL 操作维护冷却/使用状态。

本项目 [bridge.py](../../collector/bridge.py#L111) 目前仅把状态码、正文交给后续处理，429 变为固定 `RATE_LIMITED`，没有把安全的限流时间交给 Node。多个监控目标共享一组 Cookie，但目标各自的检查间隔不能代替登录会话的冷却策略。

建议面板增加：“最近验证成功时间”“限流中，预计几点重试”“需要更新 Cookie”“网络异常”。采用正常采集结果更新；有需要再提供明确的“测试 X 会话”操作，与 AI 的 hi 测试分开。不能仅因 Cookie 字段非空就显示登录正常，也不能把所有 403 解释为封号。

实现时仅传递范围校验后的额度数字、恢复时间和固定错误类别，不暴露全部响应头。冷却按登录会话及操作维护；不同操作是否共享额度不能凭空假设。缺少或不可信的 reset 时使用有上限的退避；重试保持在当前总截止内，认证错误、坏页和存储失败不能统一当作暂时网络故障。

**有一个必须避开的上游处理细节**：当前 QueueClient 遇到 `remaining=0` 且有 reset，就关闭上下文并抛出 `HandledError`，即使本次响应是带有效数据的 HTTP 200。本程序应先保存并校验最后一个成功页，再限制下一请求；如果还没覆盖旧水位，仍不能推进检查点。上游还允许部分 `errors + data` 响应继续进入解析，不能沿用为本程序的完整页成功条件。

这些分支由 [verify-transport.py](verify-transport.py) 离线验证。研究时 [PR #364](https://github.com/vladkens/twscrape/pull/364) 仍为 open、未合并，涉及限流/封禁轮换和单对象解析错误修复；不能把 PR 里的修复描述为已拥有的行为。

## 二、引用上下文与媒体：最直接的阅读体验提升

上游 [Tweet/Media 模型](https://github.com/vladkens/twscrape/blob/63f61a518e576ea5c132f1156c03dda0520d76c1/twscrape/models.py#L404) 能读取引用/转推嵌套对象、图片、视频缩略图、视频码率版本及 GIF。UserTweets 历史公开响应也包含这些结构，说明它们可随当前时间线返回，无需一律为每条另查详情。

当前我们已保留引用、转推、回复、编辑关系 ID，以及 note_tweet 长正文和完整转推正文；这些不是尚未拥有的新功能。尚未进入投递链路的是 **引用正文与媒体元数据**。

建议分两步：

1. 提取当前页已经附带的引用作者、正文摘要、链接；提供图片链接或缩略图入口及视频链接，正文翻译沿用既有规则。缺失的上下文明确保留链接，不把父推文当作坏帖，也不默认额外追查所有引用。
2. 再增加 Telegram 原生图片、相册和视频。twscrape 提供元数据，不会替本程序完成 Telegram 上传、下载大小控制或消息确认。视频码率选择、下载超时、资源限制和媒体地址范围需要单独设计，不能直接照搬上游无界并发下载示例。

不是只改模板：

- [解析器输出](../../lib/twscrape-timeline.js#L238) 丢弃这些字段；[outbox](../../lib/outbox.js#L26) 持久化时又有字段白名单。
- [mergeTweet](../../lib/twscrape-timeline.js#L149) 对多数属性严格比较。若直接添加可选媒体、引用正文或会变化的互动计数，同 ID 在两页里详略不同会产生 `TWEET_CONFLICT`。必须区分稳定身份、正文冲突、可补充信息和动态属性，同时限制嵌套层数/字段大小。
- 当前 [Telegram](../../lib/telegram.js#L62) 只调用 `sendMessage`。文本加图片的多次发送可能部分成功，需要持久记录各部分确认；单个 tweet ID 的一次确认不足以解决重试重复发送。
- 媒体拉取使用独立受控传输，不向媒体地址附带 X Cookie；新增字段不能绕过队列总容量、旧状态读取与错误处理。

[verify-content.cjs](verify-content.cjs) 已用全内存合成数据复现：引用 ID 保留但正文/媒体丢弃；额外字段经队列重新读取后丢弃；直接添加这些可选字段在两种合并顺序下均冲突。

## 三、帖子类型与关键词：先做本地策略，再增加回复来源

可先在每个监控目标配置“是否推送转推”“包含/排除关键词”，在消息里明确原创、转推、回复和引用。类型可能重叠，不能假设引用一定不是回复。关键词筛选是利用 twscrape 返回内容实现的本地功能，并非上游现成的投递策略。

必须在整页证据与覆盖验收完成后筛选，保留采集进度。当前 outbox 支持无新增待发项时更新采集水位，因此“规则只影响以后新记录”可以小步接入；但要记录过滤原因及规则版本，不能把过滤项写成已发送。改规则后追补历史需要独立的保存与回放设计，当前 7 天诊断证据不等于完整档案。

“不推送已遇到的回复”与“采集作者的帖子和回复”是两个功能。本项目只调用 UserTweets；上游有独立的 [UserTweetsAndReplies](https://github.com/vladkens/twscrape/blob/63f61a518e576ea5c132f1156c03dda0520d76c1/twscrape/api.py#L596)。后者适合监控作者在评论区发布的新信息，但需要新的操作白名单、模块解析、分页覆盖与切换基线，不能沿用原检查点便宣称过去回复也已覆盖。X 返回结果仍受权限、接口行为影响。

## 四、详情、连续讨论与 Article：有价值，但应按需补充

| 上游能力 | 适合用途 | 真实边界 |
|---|---|---|
| `tweet_details` | 已知推文的正文、文章或背景补充 | 单个目标详情不等于完整对话；解析失败与不可见不能都当作删除 |
| `tweet_replies` | 查看目标推文的直接回复 | 按 `inReplyToTweetId` 过滤，使用 ShowMoreThreads 游标，不包含所有层级后代 |
| `tweet_thread` | 获取同一 conversation 的讨论候选 | 按 `conversationId == 传入 ID` 过滤，应先确定对话根 ID；结果可能含其他作者，不等于原作者连续长帖或完整对话 |
| Article 模型 | 标题、预览、封面、可用的正文块 | 与已支持的 note_tweet 长推文不同；详情开启富正文开关，其他来源可能只有预览 |
| `editControl` | 显示编辑版本关系、更正提醒的基础 | 只有版本 ID 不等于拥有各版本正文；最新时间线不能保证发现旧帖后续编辑/删除 |

源码：[详情与对话方法](https://github.com/vladkens/twscrape/blob/63f61a518e576ea5c132f1156c03dda0520d76c1/twscrape/api.py#L372)、[Article](https://github.com/vladkens/twscrape/blob/63f61a518e576ea5c132f1156c03dda0520d76c1/twscrape/models.py#L357)、[编辑关系](https://github.com/vladkens/twscrape/blob/63f61a518e576ea5c132f1156c03dda0520d76c1/twscrape/models.py#L1210)。

建议先利用当前页已有的 Article 标题/摘要；需要全文、父帖或 thread 时作为有预算的补充任务。正文采集和持久入队先完成，补充失败保留原文，不让一条复杂长帖阻塞其他账号。若要合并连续推文为一条 Telegram 消息，还需定义等待时间、迟到续帖和已发送内容的更新方式。

## 五、List、搜索、账号资料：扩源与管理便利

上游提供 [List 时间线](https://github.com/vladkens/twscrape/blob/63f61a518e576ea5c132f1156c03dda0520d76c1/twscrape/api.py#L652)、[List 成员](https://github.com/vladkens/twscrape/blob/63f61a518e576ea5c132f1156c03dda0520d76c1/twscrape/api.py#L736) 和 [Latest 搜索](https://github.com/vladkens/twscrape/blob/63f61a518e576ea5c132f1156c03dda0520d76c1/twscrape/api.py#L287)。

- **List 成员导入**可以先做成“预览成员 → 选择新增账号”。导入后仍逐账号监控，保留数量上限、去重和各自首轮基线。这比直接接入聚合时间线小，但不减少日后的逐账号请求。
- **List 聚合**适合长期关注一组作者。使用已知 List ID，不等于提供列表搜索，也不能假设一条 List 流覆盖全部成员各自时间线的所有内容。成员增删的基线与补采规则要明确。
- **关键词搜索**适合产品、事件、主题发现。虽然默认 `Latest`，仍会受索引延迟、权限和搜索结果变化影响，不能承诺“关键词相关内容一条不漏”。需要重叠窗口及迟到结果策略，不能只取最大 ID。
- **稳定用户 ID 与资料缓存**值得作为基础改进，避免每轮重复解析用户名，并支持明确的改名提示。`user_by_id` / `user_about` 能提供资料；但缓存更新和 outbox 的用户名键迁移由我们设计，不能同名误绑用户。`user_about` 的地区、用户名变更次数/最近时间不等于完整改名清单或独立身份核验。

当前 outbox 按 username 存状态，worker 会过滤其他作者。真正的 List/Search 来源必须有独立 `sourceId`、解析与检查点，并记录来源关系；对同一投递目标按 tweet ID 跨源去重，同时保留转推的外层身份。不能直接把聚合结果传入当前单账号流程。

## 六、账号池、客户端复用与代理：按规模引入

上游 [AccountsPool](https://github.com/vladkens/twscrape/blob/63f61a518e576ea5c132f1156c03dda0520d76c1/twscrape/accounts_pool.py#L127) 支持 Cookie 会话、SQLite、按操作锁定和账号选择。池里的“账号”是登录 X 的身份，与本程序的“监控目标”不同；四个目标不意味着需要四个登录账号。

建议先做单会话健康、额度统计，再依据真实容量决定是否引入多个获授权的登录会话。需要有限等待、凭据隔离、目标分配和轮换边界；一个分页任务中切换可见性不同的会话，不能直接视为同一覆盖证明。上游默认选择不是公平轮询，没有可用账号时可能一直等待或返回 None，不能把这当作空时间线成功。

上游 `logged_in/has_session` 只判断必要 Cookie 字段存在；`login_all` 不会自动更新 Cookie 类型账号。密码、邮箱收码、TOTP 虽有实现，但需保存更多敏感材料，也不能保证覆盖所有 X 挑战。当前规模暂不建议引入。

当前桥接已经在一次目标采集内复用 HTTP 会话和签名器，但每个目标都会新建 Python 进程。可以研究同轮同凭据的有限复用，以及 user ID 缓存，以减少重复初始化。收益尚未计量；延长生命周期需要保留凭据变更失效、取消、容量/时间限制，并重新界定桥接累计请求/字节预算。上游以 username 为键的全局 signer 缓存不能直接替代这些条件。

显式代理仅在部署网络有需要时加入，不能恢复环境变量隐式代理、任意重定向或扩大 Cookie 目的地址。上游遥测与原始 dump 继续关闭。

## 七、两项不能误称为 twscrape 现成功能的可靠性工作

**采集与投递分开调度。** 当前 [worker](../../lib/worker.js#L250) 对一个账号逐条等待 AI 和 Telegram，最多处理 50 条，再进入下一个目标。增加媒体、回复或新来源会放大延迟。应让采集按计划产生持久待发项，由独立、有界且公平的投递调度处理，并保留暂停、配置代次、目标绑定和确认逻辑。账号池本身不解决这个瓶颈。

**跨轮持续补采。** 当前上限是 5 页 / 500 条 / 90 秒；超限保住旧水位，但下一次仍从最新页重来。twscrape 的 `limit=-1` 不能替代持久恢复设计。需要固定待补区间、原检查点、分页游标、页面证据引用、任务状态与预算；覆盖闭合后才能推进水位。游标失效、重复页、空页、权限变化要明确失败或重新核验，不能冒充终点。

目前证据按容量、128 个文件、7 天清理，只保护当前轮；跨轮任务引用的页面需另行保护。历史导入是否投递、投递速率、是否只建立基线也必须显式定义，避免恢复后突然大量推送。

## 八、暂不优先及容易误解的功能

- 粉丝、关注、认证粉丝、付费订阅、转推者列表适合关系分析；对当前 X → Telegram 新帖监控收益较低。互动计数是采样值，会变化，不宜加入正文冲突身份。
- Trends、社区和书签有对应方法，但先有具体用途再接。社区默认 `rankingMode=Relevance`，不能用最大推文 ID 证明时间覆盖；书签是当前登录账号自己的书签。
- 当前 API 没有任意用户点赞历史方法、通用批量 user ID 查询、独立列出所有引用帖的方法，或完整 Spaces 抓取接口。卡片元数据不等于完整 Spaces 能力。
- twscrape 的 `lang` 来自 X 数据，不是独立的语言识别/翻译引擎。本程序已经结合正文和标记判断非中文翻译，无须为此引入另一个 twscrape 功能。
- 不将自动登录、自动解挑战、Cookie 永久续期、所有旧帖编辑/删除监控、无限历史完整性列为已可直接接入的能力。

## 验证与复现

内容探针用于复现 **`b7bf16b` 研究基线**中的字段流失，当前能力扩展已改变这些行为。不能直接把历史断言用于新代码。先在项目根目录导出隔离源码（不含依赖、状态或凭据），探针会校验两份基线源码哈希：

```sh
probe_baseline=$(mktemp -d /tmp/twv2-research-baseline.XXXXXX)
git archive b7bf16be35b5df8063ba1d5a1c8de62c148c21ee lib | tar -x -C "$probe_baseline"
TW_PROBE_BASELINE_DIR="$probe_baseline" node research/twscrape-20261029-capabilities/verify-content.cjs
rm -r -- "$probe_baseline"
python3 research/twscrape-20261029-capabilities/verify-transport.py
```
