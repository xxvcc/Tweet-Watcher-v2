## 启动与验证

```bash
npm ci --ignore-scripts
npm test
npm start
```

默认入口为 `http://127.0.0.1:8788`。首次设置密码使用本机启动终端显示的一次性令牌。远程服务器开发可通过 VS Code 端口转发访问，不需要把开发服务绑定公网。

当前运行配置：

| 变量 | 默认值 | 行为 |
|---|---|---|
| `HOST` | `127.0.0.1` | 仅监听回环 |
| `PORT` | `8788` | 与第一代生产端口分开 |
| `DATA_DIR` | 本仓库 `data/` | 相对路径按项目根解析；可为第二代指定独立绝对路径 |
| `TW_RUNTIME_MODE` | `development` | 禁止采集及 Telegram 发送，包括 worker、手动测试和底层出口 |

`DATA_DIR` 的解析会核对现存祖先的真实路径，拒绝第一代生产目录 `/www/tweet-watcher` 及其子目录，也拒绝指向这些位置的软链接别名。公开静态目录 `public/` 及其子目录和软链接别名同样禁止用作数据目录，避免运行数据被静态服务公开。其他位置仍应由开发者为本实例独占使用，不与别的实例共享状态文件。

`TW_RUNTIME_MODE=legacy-live` 是显式保留的旧 Bird 运行兼容模式，会允许真实采集和发送；它不是 twscrape 模式，也不是第二代可用性的证明。当前开发与 CI 模板均使用默认 `development`。保存配置或恢复监控不能绕过默认模式；被禁用的手动测试返回 `RUNTIME_DISABLED`。

`/api/status` 的 `runtime` 字段公开当前模式、采集器标识、采集与发送是否启用以及原因。第二代数据默认存放于自己的 `data/`，未来部署可通过 `DATA_DIR` 选择 `/var/lib/tweet-watcher-v2/`，但本轮不创建或启用第二代 systemd 服务、不配置公网代理、不执行真实采集或消息投递。

[CI 模板](../.github/ci-template.yml) 已准备 Node.js 22/24 矩阵，安装锁定依赖并执行语法检查和离线应用测试。当前 GitHub OAuth 登录缺少 `workflow` 权限，且本机没有可用的 GitHub SSH 授权，因此模板尚未放入 `.github/workflows/`，自动 CI 尚未启用；启用步骤见 [CI 说明](../.github/CI.md)。

## 适配边界

目标结构是 Node 管理面板、调度与 outbox 配合 Python 单页采集器。当前不要求重做 UI、改成全 Python 或更换消息数据库。

1. 使用受控单页传输，不能把 `user_tweets_raw()` 的终止行为当成完整覆盖证据。它仍会过滤页面，详见[研究报告](../research/twscrape-20261023/README.md)。
2. 对完整响应验证所有相关 instructions、置顶、模块、可见性、错误及游标，再决定推进采集检查点。原始页证据持久化需要容量、保留期与恢复规则。
3. 明确区分无新推文、真正终点、限流、失效会话、页面不完整、重复/循环游标和预算耗尽。失败不能伪装成成功空列表。
4. Python 到 Node 的协议统一使用字符串 ID；保留原创、转发、引用、回复和编辑关系，不混淆外层推文与被引用对象。
5. 凭据限于 Cookie，不纳入密码、邮箱或 TOTP 自动登录。限制 Cookie/敏感头作用域、HTTPS 与重定向；关闭遥测和默认 dump。
6. 固定 twscrape 提交和依赖哈希；设置响应大小、页数、等待、请求与整轮截止时间。多目标监控不等于独立登录会话，账号池需要统一调度。
7. 采集检查点与 Telegram 交付确认分别维护，保留持久 outbox 的失败关闭与重启恢复语义。
