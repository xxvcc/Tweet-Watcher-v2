# 采集来源、内容与会话管理

适用版本：`0.2.0-beta.1`。本页描述该版本的功能；发布、部署和真实验证范围以[维护交接](SESSION_HANDOFF.md)与[验证摘要](VERIFICATION.md)为准。

## 来源与筛选

设置支持三类来源：账号、已知 ID 的 X List、关键词搜索。账号可选择“帖子”或“帖子与回复”。每个来源拥有独立采集检查点；切换来源类型、搜索查询或帖子/回复模式会建立新的基线，首次有效快照不会历史群发。

删除或替换来源会移除旧来源状态。存在待发送消息时，面板先列出来源和条数，必须明确确认丢弃后才能保存；取消保留草稿。服务端保存前独立核对最新队列，未确认返回 `409 PENDING_REMOVAL_REQUIRES_CONFIRMATION` 与 `removed_pending`，确认请求携带 `discard_removed_pending:true`。队列读取失败返回 500，不保存配置。

List 成员预览可勾选导入账号，保留重复检测、100 个来源总上限和首轮基线。未读完的成员列表明确显示未完成，不能当作完整 List。直接监控 List 与导入后逐账号监控是两种方式。

每个来源可配置原创、转推、回复、引用，以及包含/排除关键词。类型可重叠，任一相关类型被关闭即过滤；包含词任一命中即可，排除词优先。关键词按 Unicode NFKC 和大小写归一化做字面匹配，不是正则表达式。规则只作用于后续完成采集的新记录，已有待发送项不被悄悄删除。

完整页与覆盖验收先于过滤。被过滤的 ID、原因与规则摘要和检查点一起原子保存，不计为“已发送”；每来源保留最近 1000 条处置记录。再次修改规则不会自动重放历史。

搜索采用 Latest 和 24 小时重叠窗口，允许后续低于最新 ID 的迟到结果；首次基线之前的 ID 不推送。搜索不是完整历史档案，索引、权限和上游变化仍可能遗漏内容。已观察 ID 保留到离开采集检查点对应的 24 小时 ID 窗口；检查点停滞时不能仅按墙钟时间删除。每来源最多 10000 条，窗口内满时停止推进，不静默淘汰后重发。

同一 Telegram 目标的同一推文 ID 跨来源去重；转推保留外层独立 ID。已投递账本至少保留 25 小时，仍在任一搜索 ID 窗口内的记录继续保留；最多 20000 条，未完成发送计划预留容量，容量不足时停止新发送。更早且已离开窗口的跨来源重复不保证永久记忆。来源自己的增量检查点继续约束账号与 List 的旧记录。

## 内容与 Telegram

从当前页提取已有的图片、视频/GIF 元数据、引用作者和正文、文章标题/预览、对话关系。缺失或格式错误的可选附件不能冒充完整内容，也不能导致丢弃正文完整的父推文。重复页可补充元数据，但明确的身份或正文冲突仍失败关闭。

媒体模式：

- `links`（默认）：保留媒体入口，不发送原生附件。
- `photos`：发送图片，多图使用相册；视频保留链接。
- `all`：图片和视频可组成相册，GIF 使用动画发送。

媒体只接受固定 X CDN 的 HTTPS 地址，Telegram 服务端获取文件，本机不携带 X Cookie 下载媒体。API 请求有超时与响应限制，重定向被拒绝；大文件、不可获取资源或 Telegram 拒绝会保留未完成部分和错误，不冒充送达。

正文、引用/文章/对话背景及媒体组成有界发送计划，先持久保存，再逐部分发送与确认。重启后跳过已确认部分；主正文成功后附件失败时，不从正文重新开始。已创建的发送计划保持固定，修改内容设置影响之后尚未创建的计划。Telegram 成功但确认落盘前崩溃仍可能重发该部分，不能承诺恰好一次。

可选补充模式默认 `off`，支持 `detail` / `thread`，每次展示补充条数 1–5。原帖先持久入队，再请求有预算的补充；失败回退已捕获内容。对话可能包括其他作者，不表示原作者连续长帖或完整评论树。Article 与 note_tweet 长推文不同，缺失全文时展示已有标题/预览。面板也提供已知推文 ID 的详情/对话查看。

自动 AI 翻译仍针对主推文正文；引用、文章和对话附加文本不自动逐条调用 AI。原文、ID、关系与采集检查点不会被展示补充改写。

## 登录会话、健康与代理

原 `auth_token` / `ct0` 自动作为默认会话；可以添加额外 Cookie 会话，配置保存标签、启用状态和可选代理，凭据独立保存在私有 secrets。API 只返回是否已配置，不回显凭据。

每个会话及 GraphQL 操作独立记录剩余额度、冷却、最近成功/失败。最后一个成功页即使剩余额度为零仍保存并验收；下一次请求等待恢复。未知恢复时间采用有限退避，认证失败停止选择该凭据；正常任务在可用会话间分配，显式会话测试仍遵守限流。

Cookie 非空不等于认证成功。状态区分尚未验证、最近成功、限流、需要更新 Cookie、网络/上游异常，并显示时间。已有队列投递可以在 X 冷却期间继续运行。

一个未完成补采任务固定会话及凭据/代理摘要，不在页间自动换身份。更新 Cookie 后若旧补采无法继续，可以手动“重新开始补采”：只删除补采过程，保留原检查点和待发队列，从最新页重新验证缺口。

代理仅支持显式 HTTP(S) 地址与端口，禁止 URL 用户名密码、控制字符、隐式环境代理和跳转。支持配置不代表本机已真实验证某台代理。程序不保存密码/邮箱/TOTP，不提供自动解挑战或 Cookie 永久续期。

签名和客户端在创建后 3 分钟内最多开始 8 轮，空闲 30 秒关闭；已开始的一轮仍受独立截止、请求和字节预算约束。用户资料缓存绑定凭据，最长 15 分钟，身份冲突失效；缓存不能代替新的真实认证结果。

## 调度与持续补采

采集按来源轮询，投递另行公平调度。慢 AI 或 Telegram 不阻止后续账号采集；X 查询仍串行且有预算。暂停、配置代次、目的地绑定与未确认存储继续阻止旧任务发起新发送；已经发出的成功请求仍需持久确认。

单轮最多 5 页/90 秒；持续补采按完整页保存游标、固定区间和原始证据，跨轮/重启继续，整段覆盖闭合后才推进 outbox 检查点。完成状态在队列提交后清除，提交成功但清理前崩溃可核对检查点恢复。

单补采任务上限 100 页、1000 条、6 MiB、7 天；全局最多 32 个任务、64 MiB。原始页面嵌入私有补采文件，普通诊断证据轮转不会删除未完成任务的依据。游标循环、坏页、超容量、过期、换会话或持久化失败明确停止并保留旧检查点，不跳过缺口。

队列继续限制每来源 1000 条、全局 5000 条及 6 MiB，附加文本和发送计划也占用该预算。

## 状态兼容与测试入口

读取原版本 1 队列；使用新来源、附加内容、筛选、发送计划或跨来源账本后写入版本 2。旧版本不能解释这些字段，不能直接回退代码继续发送。完整步骤见[迁移与回退](MIGRATION.md)。

所有新查询沿用认证、CSRF、配置版本校验、单飞和进程模式控制：development 禁止外部查询；read-only 仅允许手动 X 查询；live 才允许自动采集、AI 和 Telegram。界面测试不绕过保存失败或模式开关。

新增接口：`/api/test/session`、`/api/inspect/tweet`、`/api/list/members`、`/api/catchup/reset`。来源测试沿用 `/api/test/collector`，支持 `source_key`。实际回归、浏览器和真实验证范围集中记录在[验证摘要](VERIFICATION.md)。
