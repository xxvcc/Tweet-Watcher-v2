# 第二代 twscrape 版本：仓库、目录与开发方案

> 本文保留最初规划。当前实现已进入 `0.1.0-beta.1`，twscrape 接入及只读验证已完成。最新事实见 [开发指南](DEVELOPMENT.md) 与 [验证记录](VERIFICATION.md)；下文的“当前骨架”描述的是初始化阶段。

记录日期：2026-10-23。状态：用户已授权并已创建第二代公开仓库 `xxvcc/Tweet-Watcher-v2` 与独立开发目录，本轮完成开发骨架初始化。开发版本为 `0.1.0-alpha.1`；正式发行编号和生产切换时间尚未确定。twscrape 适配不属于已完成能力，本轮不创建生产服务。

## 用户已经明确的方向

- 准备开发使用 twscrape 的第二代版本。
- 希望新版本与现有项目分开，考虑使用新的公开仓库和目录。

这里的“第一代/v1”和“第二代/v2”是架构代际名称。第一代当前已经发布的实际软件版本是 **3.5.0**；不会因代际命名而修改现有版本号。

## 已确定的仓库与目录布局

| 用途 | 仓库 | 本地目录 | 维护方式 |
|---|---|---|---|

保留现有生产路径，可以继续使用已有 systemd、代理和数据位置。第二代放在同级目录，拥有自己的 `.git`，与第一代分别打开项目和安排开发任务。两个项目通过提交移植同步公共修复，不共享可写源码目录。

独立仓库会增加两边同步安全修复的工作，但符合两代长期并行维护、分别发布的目标。第二代仓库应注明源自第一代 v3.5.0，说明代际区别、开发状态和迁移进度；旧仓库可以在新版可用时添加入口链接。

## 新仓库如何初始化

已确定保留现有 Git 历史，从已发布的 v3.5.0 基线派生。这样可以追溯认证、持久交付和页面校验的修复来源，也方便后续移植。

本轮已通过独立 Git clone 建立两个开发副本，核对对象存储没有 alternates 或本地硬链接；只取得 Git 跟踪的代码，不复制整个运行目录。历史 tag 不自动发布到新仓库，新版 Release 独立管理。第二代 `origin` 指向新仓库，旧仓库保留为只用于 fetch 的 `legacy` remote，设置 `pushurl=DISABLED` 防止误推送。

已带入：应用代码、测试、MIT 许可证及原有归属、锁文件、部署模板、研究材料，以及这份方案。继承的第一代部署模板是历史参照，不能直接用于第二代部署。

运行时 `data/`、Cookie、密码、会话密钥、Telegram 配置、`node_modules/`、Python 虚拟环境和备份均不随源码复制。新环境按锁文件单独安装依赖；需要真实采集时，再通过受限的配置流程提供登录会话。

新项目开发版本确定为 `0.1.0-alpha.1`；正式发行编号另行确定。文档明确“第二代”与包版本的区别，旧仓库继续使用 3.x 版本线。

## 服务与数据隔离

| 项目 | 第一代生产 | 第二代建议 |
|---|---|---|
| systemd 服务 | `tweet-watcher.service` | `tweet-watcher-v2.service`，进入联调阶段再配置 |
| 系统用户 | `tweet-watcher` | 独立 `tweet-watcher-v2` 用户 |
| 监听 | 当前部署 | 暂定 `127.0.0.1:8788`，启用前检查占用 |
| 应用数据 | `/www/tweet-watcher/data/` | 开发期独立 `data/`，`DATA_DIR` 支持后续 `/var/lib/tweet-watcher-v2/`；拒绝旧生产路径 |
| Python 环境 | 当前不依赖 Python 采集器 | 新版独立环境，固定 twscrape 提交和依赖哈希 |
| 会话池与锁 | 当前 Bird 配置 | 新版自己的 accounts.db、锁和等待预算 |
| 管理会话 | 当前来源和密钥 | 新版独立管理认证、密钥与 Cookie 来源 |
| 发送策略 | 现有生产发送 | 默认禁止生产发送，先做离线和只读对照 |

第一代开发副本也应使用独立端口和合成测试数据，不能靠克隆代码后直接启动来继承生产设置。初始骨架用默认 `TW_RUNTIME_MODE=development` 统一关闭采集与发送，并在代码层覆盖 worker、测试接口和底层出口；显式 `legacy-live` 仅保留旧 Bird 兼容入口。后续只读对照阶段再增加能独立控制采集和发送的模式，不能只依靠操作人员记得暂停。

开发初期无需立即增加正式域名。使用本机访问或受限预览；若两套管理面板要同时公网访问，应使用独立来源。仅换端口不能完整隔离浏览器 Cookie。正式切换时再决定将原入口转给新版还是保留两个入口。

独立数据库也不代表上游限流独立：如果两套采集器使用同一个 X 登录会话，它们仍会消耗同一会话的限流预算。只读对照需要低并发、有界请求和协调调度。

## 第二代第一阶段的技术范围

基于现有 Node 面板、认证、调度与持久发送机制增加 Python 采集器，优先验证更换采集底层的可行性。是否重做 UI、改写为全 Python 或更换消息存储属于后续独立决策。

1. 建立稳定的采集接口：目标账号、请求游标、页响应、字符串 ID、关系字段、错误类型、完整性与覆盖状态。
2. twscrape 适配采用受控单页请求层；完整页在持久化前不能成为游标或覆盖边界。未知结构、部分 GraphQL 错误、重复游标与达到抓取上限均有明确状态。
3. 保留转发、引用、回复、编辑关系及内容版本信息；不能把引用对象混作目标账号的独立推文。原始页面私有暂存需有容量、保留期和恢复规则。
4. 固定已审查的 twscrape 源码和依赖；限制 Cookie/敏感头作用域与重定向，关闭遥测和默认 dump，使用私有存储。密码、邮箱自动登录和 TOTP 种子不属于初期范围。
5. Python→Node 协议使用字符串 ID、明确版本和大小限制；凭据不进入命令参数、日志或结果流。统一控制账号池，设置请求、分页、等待和整轮时限。
6. 延续现有持久 outbox，并为新版增加能验证的“只采集、不发送”模式。采集检查点和 Telegram 交付确认分别维护。

此前研究已经说明：公开 `user_tweets_raw()` 也可能筛掉有内容页面，不能直接作为可靠分页边界。详细证据见 [twscrape 研究](../research/twscrape-20261023/README.md)。

## 开发与验收顺序

| 阶段 | 交付内容 | 进入下一阶段的依据 |
|---|---|---|
| 仓库初始化 | 新公开仓库、独立目录、许可证与来源说明、开发文档、CI | 代码可独立安装和运行离线测试，未引用生产数据 |
| 离线适配 | 单页传输、严格解析、协议、安全控制、独立存储 | 坏页不推进水位、ID 不失真、错误不伪装成空结果 |
| 只读对照 | 对同一目标记录两端 ID、正文、关系和覆盖差异 | 差异得到解释，限流及失效会话能正确分类，无生产投递 |
| 测试发送与恢复 | 独立测试接收端、重试、崩溃、状态损坏和目标变更验证 | 已采集内容可恢复，发送确认与检查点规则成立 |
| 生产切换 | 停止旧版发送、快照、迁移、验证、新版独占发送权 | 迁移数量与状态核对通过，回退流程可执行 |

切换时须处理旧版在途请求和未发送 outbox，导入已发送 ID/覆盖状态，避免重新建立基线而漏发或大量重发。若新版已经发送过消息，回退前要处理新增确认记录；直接启动旧数据快照可能重复发送。旧版本、原始数据快照和迁移映射保留作为恢复依据。

## 两代如何持续维护

- 第一代修复在自己的开发副本完成，走原仓库发布流程，再部署到第一代生产路径。
- 认证、代理、发送和状态安全修复需要评估两边是否受影响。可用 cherry-pick 或独立实现移植，记录来源提交并在目标仓库运行相应测试。
- twscrape 特有的兼容和协议改动进入第二代；第一代仅在确有需要时接收可复用部分。
- 当前范围不要求独立维护 twscrape 上游 fork。若适配原型必须修改上游内部实现，再记录最小补丁及维护策略。
- 不因建立第二代就归档第一代；停止第一代维护应由实际使用情况和迁移结果决定。

本文件是第二代方案的后续维护入口。第一代开发副本提供入口说明；第一代生产目录不承担第二代文档维护。
