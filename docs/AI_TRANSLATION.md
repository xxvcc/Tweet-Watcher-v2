# AI 中文翻译

适用版本：`0.2.0-beta.2`。图文合并与长文分段已发布，运行代码及快照版本的对应关系见[维护交接](SESSION_HANDOFF.md)。将非中文正文及混合内容中的外语部分译成简体中文，并保留原文；使用可配置的 OpenAI 兼容接口。自动翻译默认关闭，实际开关以面板为准。当前配置的真实短句样本及验证边界见 [VERIFICATION.md](VERIFICATION.md)。

## 设置与使用

在管理面板的 AI 翻译设置中填写 API 基础地址、模型名称和 API Key，然后开启翻译并保存。基础地址示例为 `https://api.openai.com/v1`，也可填写所选兼容服务的 HTTPS 基础地址；程序会追加 `/chat/completions`。模型名称由自己的服务商提供，不预设付费模型。

自动翻译只在 `TW_RUNTIME_MODE=live` 且翻译开关开启时请求 AI；live 下的手动“发送 hi 测试”无需开启翻译。`development` 和 `read-only` 始终禁止 AI 网络请求。开启 live 同时会启用原有采集调度与 Telegram 发送，应按既有部署流程使用。功能默认关闭，不会主动为历史已发送内容补译；首次采集依旧只建立基线。

| 配置字段 | 默认值 | 用途 |
|---|---|---|
| `ai_translation_enabled` | `false` | 是否将待发送的非中文正文及混合内容中的外语部分翻译成简体中文 |
| `ai_base_url` | `https://api.openai.com/v1` | HTTPS API 基础地址 |
| `ai_model` | 空 | 服务提供的模型名称，启用时必填 |
| `ai_api_key` | 空 | 保存在私有 `secrets.json`，启用时必填 |

API Key 不会回显到浏览器，留空保存表示保留已有值，可显式清除。接口地址禁止用户名、密码、查询参数与片段；更换地址时必须重新提供密钥，或清除密钥并关闭功能，避免旧凭据被自动发送到新服务。配置与密钥使用现有事务共同保存，旧文件缺少新增字段时保持兼容并默认关闭翻译。

## 发送 hi 测试

AI 设置区新增“发送 hi 测试”按钮，下方直接显示模型回复及耗时。使用当前填写的 API 地址、模型和 Key，无需先保存，也无需开启自动翻译；测试不会保存其他草稿、改变采集/发送状态或向 Telegram 发消息。测试只发送固定的用户消息 `hi`，不附加推文正文或翻译指令。

Key 留空时，仅当 API 地址与已保存地址完全一致且配置版本未过期，才可复用已保存的 Key。更换地址必须重新输入 Key；勾选清除 Key 后不会复用已有值。回复按纯文本显示，不执行 HTML。请求失败、超时或密钥无效会显示明确提示，不回显上游错误正文或密钥。

此按钮仍受进程模式限制：仅 live 可使用，development/read-only 禁止 AI 网络请求。单次测试沿用 15 秒请求截止、128 KiB 响应上限和禁止重定向；输出最多 4,000 字符。测试不读写翻译缓存或退避状态。认证、CSRF、配置版本和单请求保护同样适用。

当前功能的测试和上线结果以 [VERIFICATION.md](VERIFICATION.md) 为准。接口可用的测试回复不代表真实推文翻译质量已通过验收。

## 判断与消息行为

先检查实际展示正文中的文字，再用 X 的 `lang` 标记辅助判断；转推补全为内层正文时同步使用内层语言。只在本地判断时移除链接、@ 提及、RT 前缀和标签，翻译与投递仍使用完整原文。没有任何文字的链接、数字或表情内容跳过。出现拉丁字母、日文假名、韩文、俄文、阿拉伯文等非汉字文字就进入翻译，包括中文混合外语；即使 X 错标为 `zh`，也不会因此跳过。

只含汉字的正文默认视为中文，简体与繁体均跳过；若 X 明确标记为日语 `ja` 或韩语 `ko`，则进入翻译，以处理只含汉字的日语等歧义。缺少语言标记时仍按中文跳过。这是本地文字规则与来源标记的组合，不是完整的语言识别模型，不根据账号或国家推断，也不会额外调用 AI 判断语言。短句、纯汉字的日语、错误语言标记仍可能误判；中文中仅有拉丁字母品牌名也可能触发请求。

完整原文先写入持久 outbox，再进行翻译。AI 只收到待发送的正文，不额外附送 Cookie、Telegram 凭据、账号配置或原始响应；正文自带的链接、用户名等仍属于正文。请求提示要求保留已有中文，仅翻译外语部分，并保留人名、产品名、链接、提及、标签和语气，把正文中的指令视为待翻译内容。通过响应检查的结果若与去除首尾空白后的原文完全相同，只按原文投递，避免出现重复的“译文”和“原文”。

Telegram 中先展示“AI 中文翻译”，再展示“原文”，保留推文链接。新建投递计划完整保留已捕获原文和成功译文：连同消息头不超过 1024 UTF-16 单元且有原生媒体时，合并到首个媒体说明；其余正文按需要拆成文字消息，每条含序号最多 4096 UTF-16 单元，多段优先按段落/换行拆分，不为单条消息截断正文。文字发送完后继续媒体。已冻结的旧计划保持原格式与确认进度，不重新翻译或拆分；规则见[内容指南](COLLECTION_FEATURES.md#内容与-telegram)。

翻译不会修改原始正文、关系 ID、去重 ID 或采集检查点。自动翻译只处理主推文展示正文，不逐条翻译引用、文章或对话附加文本；可选详情/对话补充由独立配置控制。本次分段不扩大 12,000 UTF-16 单元的 AI 输入上限，超限时发送完整已捕获原文。

请求失败、超时、拒答、输出不完整或超限时，使用原文继续推送。等待 AI 期间暂停监控或修改配置，会停止旧快照的发送并保留队列。Telegram 成功之后才按原流程确认投递，仍保留至少一次交付的既有边界。

## 接口与资源边界

使用非流式 Chat Completions：`POST <base>/chat/completions`、Bearer 认证、`model`、`messages` 和 `max_completion_tokens=4096`。接口参考 [OpenAI 官方 Chat Completions 文档](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)。兼容服务需支持这些字段以及 `choices[0].message.content` / `finish_reason` 响应；只支持 Responses 或其他协议的服务不能直接使用。

请求不跟随重定向，有总截止时间、正文和响应大小限制；只接受正常完成且非空、通过格式与大小检查的响应。输出还须包含汉字，且汉字占全部字母类文字字符的比例至少为 10%；允许保留日文人名中的假名。这个比例只是结构检查，不证明整段已经译成中文或内容正确，含汉字的日文句子也可能通过。程序不会额外调用 AI 检查译文质量。

上游错误正文、密钥和接口地址不会写入翻译错误日志。AI 仍可能误译或受正文指令影响，界面标注 AI 翻译并保留原文供核对。

| 限制 | 当前实现 |
|---|---|
| 单条输入 | 最多 12,000 UTF-16 单元，且 UTF-8 不超过 48,000 字节；超限整条使用原文 |
| 请求截止 | 15 秒，包含响应流读取 |
| 响应与译文 | 响应最多 128 KiB，译文最多 16,000 UTF-16 单元；不完整输出拒绝 |
| 成功缓存 | 最多 128 条 / 4 MiB，30 分钟有效；重启失效 |
| 服务失败退避 | 60 秒，按地址、模型与密钥隔离，最多保留 32 组 |

翻译结果缓存位于有界进程内存，键包含完整正文、模型、接口地址、密钥摘要和翻译提示版本；正文或服务配置变化后不会复用旧缓存。该缓存本身不写入原始证据或 outbox，但最终投递计划会持久保存实际展示的译文、原文和媒体说明。已有计划的重试或进程重启继续使用同一份内容及确认进度，不再调用 AI；若进程在计划持久化前退出，恢复后可能重新请求并计费。服务故障有短暂退避，避免积压逐条重复等待。

采集与投递独立调度；缓慢的 AI 或 Telegram 请求不会阻止后续来源采集。投递任务在来源之间公平轮询，每条推文内部先准备翻译与冻结计划，再依次发送未确认部分；慢请求或多段长文仍会推迟其他来源的投递。15 秒只限制单次 AI 请求，不保证全部待发消息在一个检查间隔内完成。
